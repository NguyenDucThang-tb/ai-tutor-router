# Phase 3A collection protocol

Phase 3A prepares paired real-model observations and correctness-based supervision; it does not train or calibrate a router. GSM8K's official test split is frozen and excluded from collection plans, prompt/evaluator development, label export, and future routing training. Use validation for a small pipeline pilot; use train only for later approved collection. Keep model and prompt settings unchanged within one run.

`python -m experiments.collection_plan --split validation --samples 10 --seed 42` creates a deterministic plan stratified by task type, quartiles of `char_count`, and quartiles of `math_symbol_count`. Symbol count is only a query-derived complexity proxy, not an asserted difficulty label. Within-stratum ordering is seeded by SHA-256 and selection rotates through sorted strata. This is a reproducible balanced pilot plan, not a population-weighted representative sample; report its selected distribution.

Pass the resulting file to both offline preflight and benchmark execution: `python -m experiments.preflight --config configs/phase3a_pilot.example.yaml --collection-plan collection_plan.json` and `python -m experiments.benchmark run --config configs/benchmark_mock.yaml --collection-plan collection_plan.json`. Both default to validation. For train collection, specify `--split train` to preflight and benchmark. The plan binds the dataset revision, complete processed-dataset checksum, split, ordered sample IDs, sample count, sample-ID checksum, and canonical plan hash. Both commands reject stale or malformed plans, and the runner fails if the request cap cannot cover every planned paired execution. The run manifest, Run ID, per-record provenance, replay records, and training-label manifest retain the plan identity. A changed plan has a different Run ID and cannot resume the old SQLite task set. Existing Phase 2 runs without plans retain the explicit `legacy_sorted_prefix_v1` selection path; that compatibility path is not a stratified pilot.

Training-data export from a planned run must receive the same source file with `--collection-plan`. The exporter checks plan identity and sample membership and recomputes every automatic evaluation from stored output and the source answer before accepting a label. Plan hashes provide integrity and reproducibility, not a signature or proof that an author-selected plan is representative.

The paired Phase 2 runner uses one sample ID per small/strong execution, SQLite leases/fencing, request-attempt reservations, and explicit uncertainty recovery. It retains failures and incomplete pairs. No exactly-once provider execution is promised. Recovery uses the existing checkpoint and explicit retry/reissue approvals. Never replay an uncertain paid outcome by default.

## Latency and evaluation

Report model-only, gateway, feature extraction, router decision, queue, evaluator, and pipeline metrics separately. Pipeline latency begins before feature extraction and includes scheduling queue time. Model-only comparison uses primary model attempt durations; it excludes router and queue overhead and fallback time is reported separately. A failed or unsupported output remains in reliability denominators. Evaluator `unparseable`, `unsupported`, and `ambiguous` states are unknown correctness, not incorrect.

`python -m experiments.analysis review-sample --records ... --per-status 5 --seed 42` prepares a deterministic review sample across correct, incorrect, unparseable, unsupported, and ambiguous outputs. Rows are never marked reviewed; human annotations require an actual reviewer, timestamp, rationale, and adjudication metadata when applicable.

Paired bootstrap summaries resample sample pairs with a recorded seed and list unknown, failed, ineligible, and incomplete pairs outside the determinate paired denominator. The function does not compute bootstrap intervals for mock/replay records. Oracle accuracy is an upper bound using realized outcomes, not an available router or evidence of achievable savings. Mock/replay records cannot support model-quality claims.
