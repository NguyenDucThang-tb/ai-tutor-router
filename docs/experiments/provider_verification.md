# Provider verification (checked 2026-11-22)

This review uses public official provider documentation and the locally installed locked LiteLLM package. It makes no account calls and reads no credentials. Public documentation, offline package inspection, account access, and paid authorization are separate evidence levels.

The low-cost **Gemini pair is the simplest candidate to retain for protocol preparation**, because the exact model mapping exists in the pinned LiteLLM package and the current plan already names it. This is a tooling recommendation only. Account/model access, effective pricing, and a safe bill ceiling remain unverified, so it is not a pilot recommendation or authorization. OpenAI's `gpt-6.2-sol` exact-ID mapping was not found in the locked fallback data; do not substitute an alias. Anthropic counting remains an estimate and its exact request contract is unverified.

The application sends two text messages (`system`, then `user`) through LiteLLM `acompletion`, with explicit `timeout`, `num_retries=0`, `max_retries=0`, `temperature`, `max_tokens`, `seed`, API key, and optional API base. The runner owns retry/fallback behavior. It does not pass tools, grounding, or prompt-cache controls. The gateway parses model identity, usage, and optional cost fields. These parsed fields do not prove the provider invoice's complete billable categories. LiteLLM package import can try to fetch its remote model-price map; provider verification deliberately avoids importing LiteLLM, and offline tests read the installed package data directly.

## Architecture assessment

1. **Documented:** model IDs, public prices, context/output limits, token-count APIs, LiteLLM provider adapters, and provider-level limits are covered by linked official documentation. These are public contracts, not project account evidence.
2. **Offline tested:** frozen GSM8K/plan integrity, deterministic evaluator and paired runner, fake gateway calls, SQLite leases/fencing/reservations, and exact locked Gemini model-map entries. No provider request/response behavior was exercised.
3. **Account-specific and unavailable here:** API credentials, model entitlement, region availability, live rate limits, effective service tier/prices, billing account/project/workspace, and hard-limit settings. The offline verifier reads none of these.
4. **Required for paid admission:** exact model identity, current price evidence, exact request token upper bound, output/reasoning limits, complete billing categories, approved full-attempt exposure, account/model access, signed frozen-run approval, and an external spend ceiling with acceptable scope and enforcement.
5. **SQLite-only controls:** fenced claim ownership, task/request accounting, atomic local reservation against the run manifest, durable invocation intent, uncertainty retention, and result recovery. Those controls cover this database/run only.
6. **External controls:** provider project/org/workspace limits and invoices are enforced and reported by provider systems; the documented limits are delayed, shared, or not account-verified. Local reservations do not cover external processes or unrelated usage.
7. **Provider invocation paths:** the benchmark runner calls the centralized gate, then uses the SQLite reservation lifecycle before LiteLLM. Separately, `app.main` constructs a LiteLLM gateway and `app.service.TutorService.ask` calls it directly. That ordinary tutoring path does not use the benchmark gate or SQLite ledger. If `TUTOR_PER_REQUEST_BUDGET_USD` is set, the gateway refuses because no cost estimator is configured; if unset, a configured LiteLLM app can reach the provider. This path remains an unbounded spend risk and was not invoked.
8. **Identity consistency:** the benchmark reservation/intent is bound locally to the claim, run, model request, dataset/plan, and the signed approval digest. Provider account identity and API base are not established by that local binding. The gateway records response model when supplied, otherwise falls back to the requested model; therefore executed provider identity is not verified unless provider response metadata confirms it. LiteLLM calculated cost and token totals are not a provider invoice and do not currently cover all reasoning/cache/tool billing categories.

The token counter used for admission is intentionally `UnsupportedTokenCounter`: it returns `UNKNOWN`. The exposure calculator builds the exact two-message request body used by the gateway and includes configured maximum output and every retry/fallback model, but fails closed before reservation when it cannot establish a verified input upper bound and complete prices. Provider `countTokens` endpoints are not silently promoted from estimate to `VERIFIED_UPPER_BOUND`.

| `BILLING_SCOPE_VERIFIED` | **No.** No project, organization, workspace, tier, or cap setting was inspected. |
| `PAID_EXECUTION_AUTHORIZED` | **No.** The prepared artifact is unsigned and `NOT_APPROVED`; the centralized gate blocks. |

No dated immutable model snapshot is recorded for the proposed IDs; the approval binds exact API model strings and requires executed-model identity to be recorded. Rate limits are tier/project/account-specific and can change. Public region lists were not audited for account eligibility; organization membership, effective price tier, and active model access remain unknown. OpenAI says project and organization hard limits are enforced asynchronously and recorded spending may slightly exceed the configured limit. Anthropic publishes organization spend/rate limits but no account state was examined. Gemini states project spend caps are experimental and subject to overages during about a ten-minute billing-data delay. None of these facts proves an isolated, synchronous per-run ceiling.
